## Context

Project Ember 基于 Godot 4.6 的火焰纹章风格 SRPG，当前主流程（boot → menu → story → battle → result）存在多处空白页、状态跳转不一致、战斗回合未闭环、UI 耦合严重等问题。6 个子阶段均需在现有场景和脚本结构上改造而非重写，优先保证主流程稳定后再深入各项细化。

## Goals / Non-Goals

**Goals:**
- 主流程从启动到进入战斗全程无空白页、无卡死、无需手动干预
- 玩家能完成一回合完整操作链（选中→显示移动范围→移动→攻击/等待），敌方 AI 能自动完成一回合
- 胜负判定正式接入实际流程，胜利/失败后正确路由到结算或返回
- 所有 UI 面板（主菜单/剧情对话框/战斗HUD/行动菜单）按统一布局基线显示，缩放后不漂移
- 首关所需 JSON 数据全部可加载，地图/单位/武器/剧情引用关系不漂移
- 新游戏/继续游戏/战后保存可正常恢复，存档版本升级有明确约束
- 场景契约、数据 schema、开发/提交检查清单均形成稳定防线

**Non-Goals:**
- 不涉及新职业、新地图、新章节扩展
- 不做复杂成长系统、完整技能树
- 不做高级演出系统、大幅美术替换、大规模 UI 美化
- 不涉及联机、MOD、编辑器工具
- 不涉及第二关及以后内容

## Decisions

### 1. 按子阶段顺序执行，禁止并行跳跃
- **理由**：主流程不稳时，后面所有修补都会反复返工；战斗没闭环时，UI 和数据容易做成假完整。严格按 6 阶段顺序推进。
- **备选方案**：各阶段并行 → 否定，因为依赖链太强，返工成本极高。

### 2. GameState.phase 作为唯一状态源
- **理由**：当前 phase 与场景可能不一致。所有场景切换决策必须通过 GameState 路由，禁止脚本直接调用场景切换。
- **备选方案**：SceneManager 独立控制 → 暂不引入中间层，减少改动面。

### 3. UI 通信采用信号机制
- **理由**：消除"脚本顺便改 UI 控件"的耦合。UI 面板只通过信号监听业务事件，不直接调用业务逻辑。
- **备选方案**：UI Manager 单例 → 当前规模下信号足够，避免过度设计。

### 4. JSON schema 走静态校验
- **理由**：数据加载时做 schema 校验（字段存在、类型正确），不在运行时靠默认值兜底。缺失关键数据直接报错。
- **备选方案**：运行时默认值 → 否定，掩盖问题导致数据漂移。

### 5. 存档字段版本化
- **理由**：存档 schema 加 version 字段，加载时按版本号做迁移。不允许跨版本直接读取。
- **备选方案**：兼容读取 + 默认值 → 否定，复杂度随版本增长不可控。

### 6. UnitActor / TurnManager / BattleController 职责裁切
- **UnitActor**：单单位行动操作（移动、攻击、技能、状态更新），不决策
- **TurnManager**：回合调度（玩家/敌方/NPC 切换、行动队列管理）
- **BattleController**：战斗整体编排（胜负判定、战斗结束条件检查、回调主流程）
- **理由**：当前三者职责边界模糊，导致回合状态同步混乱。

## Risks / Trade-offs

- [范围蔓延] → 严格锁定 6 阶段边界，非 MVP 内容一律标记"本阶段不做"并归档
- [现有代码耦合深] → 改造时优先加契约断言，不改动过多已有逻辑，逐步收敛
- [Godot 场景编辑 vs 脚本配置] → 优先脚本配置化，减少对场景文件的手动依赖
- [存档格式变化破坏已有存档] → version 字段 + 迁移函数，破坏性变更标记 BREAKING
- [AI 修复导致测试不稳定] → 每个子阶段完成后跑一遍手测链路，输出通过/失败记录
